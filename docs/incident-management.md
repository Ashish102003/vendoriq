# Incident Management — Phase 6B

This document describes the Phase 6B **Incident Management** module for
VendorIQ. It builds on the vendor, contract, and purchase order modules and
introduces a new `incidents` table for recording vendor-related operational
issues and tracking them to resolution. It supplies the operational-incident
data that the Phase 7 Vendor Performance Engine will use.

---

## Scope

**In scope**

- An `incidents` table with strict data integrity rules
- CRUD API (create / read / update — no delete) plus statistics
- A vendor-level incident summary endpoint
- Professional frontend module (directory, report/edit form, detail page)
- Vendor profile integration via an Incident Summary section
- A workflow with explicit status transitions and immutable closed records
- Role-based access control

**Out of scope (by design)**

- Complaints and reviews
- Vendor performance scores, rankings, or risk scores (Phase 7)
- Analytics dashboards, charts, and recommendations
- Machine learning and AI features
- Deleting incidents (records are never deleted)

## Data Model

| `id`              | BigInteger      | No       | PK      | Auto-increment primary key                 |
| `incident_number` | String(20)      | No       | —       | `INC-%06d`, globally unique (indexed)      |
| `vendor_id`       | BigInteger (FK) | No       | —       | `vendors.id`, `RESTRICT`, indexed          |
| `contract_id`     | BigInteger (FK) | Yes      | —       | `contracts.id`, `RESTRICT`, indexed        |
| `purchase_order_id` | BigInteger (FK) | Yes    | —       | `purchase_orders.id`, `RESTRICT`, indexed  |
| `title`           | String(150)     | No       | —       | Short summary                              |
| `description`     | Text            | No       | —       | Full incident details                      |
| `incident_type`   | Enum/String     | No       | —       | `DELIVERY`, `QUALITY`, `SERVICE`, `CONTRACT`, `COMPLIANCE`, `COMMUNICATION`, `DOCUMENTATION`, `PAYMENT`, `OTHER` |
| `severity`        | Enum/String     | No       | —       | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`        |
| `status`          | Enum/String     | No       | `OPEN`  | `OPEN`, `IN_PROGRESS`, `RESOLVED`, `CLOSED` (indexed) |
| `reported_date`   | Date            | No       | —       | When the incident occurred / was reported  |
| `due_date`        | Date            | Yes      | —       | Target resolution date                     |
| `resolved_date`   | Date            | Yes      | —       | Set automatically on Resolved/Closed       |
| `impact_score`    | Integer         | No       | —       | 1–10 (checked)                             |
| `reported_by`     | BigInteger (FK) | No       | —       | `users.id`, `RESTRICT`, indexed, always the authenticated user |
| `assigned_to`     | BigInteger (FK) | Yes      | —       | `users.id`, `RESTRICT`, indexed, must be an active user |
| `resolution_notes`| Text            | Yes      | —       | Required for Resolved/Closed (422)         |
| `created_at`      | DateTime        | No       | `now()` | Timestamp mixin                            |
| `updated_at`      | DateTime        | No       | `now()` | Timestamp mixin                            |

### Relationships

- `vendor` → the vendor associated with the incident (required, immutable)
- `contract` → optional linked contract (must belong to the vendor)
- `purchase_order` → optional linked purchase order (must belong to the vendor
  and match the linked contract)
- `reported_by_user` → the reporting user (exposed as `reported_by_user`)
- `assigned_to_user` → the currently assigned user (exposed as
  `assigned_to_user`; nullable)
- Back-references added to `Vendor`, `Contract`, `PurchaseOrder`, and `User`
  (`incidents`, `incidents_reported`, `incidents_assigned`)

### Check constraints

- `ck_incidents_impact_score_range`: `impact_score BETWEEN 1 AND 10`
- Non-applicable here (phase uses app-level transition + date validation)

## Reference Numbers

- Format `INC-%06d` (e.g. `INC-000001`).
- Generated by the backend by taking `MAX(suffix) + 1` for all existing
  incidents; if the number is already taken by a concurrent insert the
  transaction rolls back and retries (up to a small retry budget) before
  raising 500. The number is never client-supplied.

---

## Status Workflow

Allowed transitions:

| From          | Allowed to                         |
| ------------- | ---------------------------------- |
| `OPEN`        | `IN_PROGRESS`, `RESOLVED`          |
| `IN_PROGRESS` | `RESOLVED`                         |
| `RESOLVED`    | `CLOSED`                           |
| `CLOSED`      | *(none — immutable)*               |

Rules:

1. New incidents are **always created as `OPEN`** (a `status` supplied at
   creation is ignored).
2. An explicit **transition guard** rejects any move that is not in the table
   above with 422 **"Invalid status transition from X to Y."**
3. When a status becomes `RESOLVED` or `CLOSED`:
   - `resolved_date` is auto-set to today if not provided (an explicit value
     is honored, but must not be before `reported_date`).
   - `resolution_notes` must be non-empty (422 **"Resolution notes are required
     when resolving or closing an incident."**).
4. A `CLOSED` incident cannot be modified at all — updates return 409
   **"The incident is closed and can no longer be modified."**

---

## Validation Rules

1. **Vendor is required** and must exist (404 `"Vendor not found"`).
   `vendor_id` is immutable on update.
2. **Contract exists and belongs to the vendor** — 404 `"Contract not found"` or
   422 `"The selected contract does not belong to the selected vendor."`
3. **Purchase order exists and belongs to the vendor** — 404
   `"Purchase order not found"` or 422
   `"The selected purchase order does not belong to the selected vendor."`
4. **Purchase order contract match** — if a purchase order has a linked
   contract, it must match the selected contract; otherwise 422
   `"The selected purchase order is linked to a different contract."`
5. **Title** — required, 3–150 characters.
6. **Description** — required, at least 3 characters.
7. **Dates** — `reported_date` required; `due_date` when present must not be
   before `reported_date` (422 `"due_date must not be before reported_date"`).
8. **Impact score** — integer 1–10.
9. **Assignment** — `assigned_to` must reference an active user
   (422 `"Assigned user not found"`); `null` clears the assignment.
10. **`reported_by` is never client-supplied** — always set to the authenticated
    user's id by the backend.

For updates, the full **merged state** is validated (existing fields + provided
fields), so partial updates cannot introduce an inconsistent record.

## API Endpoints

| Method | Path                                  | Roles                                   | Description |
| ------ | ------------------------------------- | --------------------------------------- | ----------- |
| GET    | `/api/v1/incidents`                   | Any authenticated user                  | Paginated list with search/filter/sort |
| GET    | `/api/v1/incidents/statistics`        | Any authenticated user                  | Per-status/severity counts, overdue, avg impact |
| GET    | `/api/v1/incidents/{incident_id}`     | Any authenticated user                  | Incident detail |
| POST   | `/api/v1/incidents`                   | Admin, VM, Procurement Manager, Project Manager | Report an incident |
| PATCH  | `/api/v1/incidents/{incident_id}`     | Admin, VM, Procurement Manager, Project Manager | Update / change status |
| DELETE | `/api/v1/incidents/{incident_id}`     | —                                       | Not allowed (405) |
| GET    | `/api/v1/vendors/{vendor_id}/incident-summary` | Any authenticated user        | Vendor-level incident summary |
| GET    | `/api/v1/users`                       | Any authenticated user                  | User list (assignment picker) |

### Query parameters (list endpoint)

- `page`, `page_size`
- `search` — matches title, description, incident number
- `vendor_id`, `contract_id`, `purchase_order_id` — relationship filters
- `incident_type`, `severity`, `incident_status` — type/severity/status filters
- `date_from`, `date_to` — reported-date range
- `sort_by` — one of `incident_number`, `reported_date`, `due_date`,
  `impact_score`, `incident_type`, `severity`, `status`, `created_at`,
  `updated_at`
- `sort_order` — `asc` or `desc`

### Statistics payload

```json
{
  "total_incidents": 4,
  "open": 1,
  "in_progress": 1,
  "resolved": 1,
  "closed": 1,
  "critical": 1,
  "high": 1,
  "medium": 1,
  "low": 1,
  "overdue": 2,
  "average_impact_score": 6.5
}
```

When there are no incidents all counts are zero and `average_impact_score` is
`null`.

### Vendor incident summary payload

| --------------------- | :---: | :------------: | :-----------------: | :-------------: | :-----: |
| View incidents        | Yes   | Yes            | Yes                 | Yes             | Yes     |
| View statistics       | Yes   | Yes            | Yes                 | Yes             | Yes     |

perform this action."**

## Frontend

### Pages

- `/incidents` — incidents directory
- `/incidents/new` — report an incident
- `/incidents/:incidentId` — incident detail
- `/incidents/:incidentId/edit` — edit an incident

### Directory page

- Stats strip: **Total Incidents**, **Open**, **In Progress**, **Critical**,
  **Overdue**
- Search box (placeholder `Search incidents...`), vendor, severity, and status
  filters plus reported-date range
- Sortable table columns: impact, severity, status, reported date, plus
  reference, vendor, and actions
- Reference column shows `INC-000001` + title
- Overdue cells render an **Overdue** callout next to the status badge
- Empty state: title `No incidents found`, message `Vendor-related issues and
  operational incidents will appear here.`
- Report buttons shown only to authorized roles

### Report / edit form

Four sections:

1. **Incident Context** — vendor (required, immutable after creation), optional
   contract and purchase order (vendor-scoped cascade, disabled until a vendor
   is selected).
2. **Incident Details** — title, description, type, severity, impact score
   (`n / 10`), reported date, optional due date.
3. **Assignment** — assigned-to user (loaded from `/api/v1/users`) and the
   reporter (always the authenticated user).
4. **Incident Status** — new incidents are always Open (read-only field); on
   edit the status select shows only the legal transitions, and resolution
   notes are required when moving to Resolved or Closed.

### Detail page

- Status + severity badges, overdue callout, reported-by line
- Description and Resolution sections
- Vendor / contract / purchase order cards
- Side cards: Details (type, severity, impact, dates), Assignment, system
  information
- **Update Status** modal (transition-aware, requires resolution notes for
  Resolved/Closed) and Edit button gated by role; neither appears for Closed
  incidents.

### Vendor detail page

An **Incident Summary** section displays real data from
`/api/v1/vendors/{id}/incident-summary`: total incidents, open/in-progress,
critical/high, resolved, closed, and average impact, plus a quick link to the
vendor-scoped incidents directory.
